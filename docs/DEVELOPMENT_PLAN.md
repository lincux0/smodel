# 小模型信息合集网站分阶段开发方案

版本：1.0
制定日期：2026-10-01
项目目录：`D:\smodel`
状态：阶段一完成；阶段二开发与本地验证完成，等待预览视觉审阅

## 1. 项目目标

建设一个开源的小模型信息网站，帮助用户按用途和设备条件选择模型，理解其能力、主要特点与限制，并获得可靠的获取和部署指引。

网站的核心使用路径：

> 明确任务 → 筛选候选模型 → 查看能力证据与运行条件 → 比较模型 → 获取与部署。

高级感、材质表现与流畅自然的动效是核心交付要求，应在早期通过真实内容和可交互页面验证。

### 1.1 已确认的首版方向

- 中文优先，保留模型原名和官方标识。
- 个人非商业运营，部署于 Vercel Hobby。
- 数据由维护者人工导入、核实与维护，后续逐步增加自动采集。
- 使用 Astro 静态生成、React 局部交互、TypeScript 和文件化内容。
- 采用精密产品目录的视觉方向，以银灰、石墨和克制的深青色形成层次。
- 首版优先完成模型目录、模型详情、同用途对比、部署指南和方法说明。

### 1.2 首版范围与边界

首版目标为 20–30 个完整模型条目，覆盖文本与代码、视觉理解、向量检索、重排、语音识别、语音合成和 OCR 等用途。

语言模型主要收录总参数约 10B 以内的型号；其他任务结合实际部署体积和资源需求判断。该阈值是本站编辑规则，不代表行业统一定义。超过边界的型号只有在存在明确的轻量部署价值时才收录，并说明原因。

首版暂不建设账户系统、评论、在线管理后台、站内模型推理、模型权重托管和自动发布采集内容。维护者可通过文件或 GitHub 网页编辑维护数据。

## 2. 内容与数据规范

### 2.1 模型身份与分类

- 一个条目对应一个明确的模型版本或型号，不用家族介绍代替具体型号的信息。
- 模型可以具有多个用途标签，输入与输出模态分别记录。
- Base、Instruct、推理变体与量化部署版本应明确区分。
- 分别记录总参数、激活参数、有效参数及统计口径；缺失数据保留为空。
- 分别记录原生上下文、扩展上下文与扩展条件。
- 分别说明权重许可、代码许可、训练资料开放程度，不将开放权重直接等同于完整 AI 开源。

### 2.2 能力呈现

模型详情先说明“擅长什么、适合什么、主要限制”，随后展示对应证据。首页与目录不使用跨用途统一智能总分。

| 模型类型 | 能力展示重点 |
| --- | --- |
| 文本与代码 | 指令遵循、知识、推理、代码能力，中文表现单独说明 |
| 视觉理解 | 图像理解、文档理解、相关任务评测 |
| Embedding / reranker | 按语言、数据集和任务展示检索或重排指标 |
| 语音识别 | WER / CER、语言、数据集与实时性 |
| 语音合成 | 发音、音色、人类偏好或 MOS、运行速度 |
| OCR | 检测、识别、版面或表格能力及各自指标 |

所有能力依据标注为官方报告、第三方评测、本站实测或编辑判断。只有条件兼容的结果才允许排序比较。下载量与点赞量仅表示关注度。

### 2.3 最小数据结构

使用三个逻辑层次，首版可嵌套存储在每个模型的 JSON 文件中，无需数据库。

| 层次 | 必要字段 |
| --- | --- |
| 模型 | 稳定 ID、名称、家族、版本、用途、模态、参数与口径、上下文、语言、许可、简介、特点、限制、官方链接、最后核实日期 |
| 部署方案 | 运行时、适用系统、格式、量化、下载来源、依赖、步骤、设备条件、验证状态与日期 |
| 评测记录 | 任务、数据集、语言、指标、数值、单位、指标方向、版本、测试条件、来源、评测日期与采集日期 |

结构化元数据使用 JSON，长篇介绍与公共部署指南使用 Markdown，通过稳定 ID 关联。维护模板是文档，避免创建会被误当作正式条目的示例数据。

### 2.4 数据可信度与维护规则

- 参数、能力、许可和部署说明应有可追溯来源，优先使用官方模型卡、仓库和文档。
- 未知值保留为空，界面区分“未提供”“未核实”和“不适用”；不得用 0 代替未知值。
- 硬件条件区分实测与估算，记录设备、运行时、量化、上下文和测试条件；文件体积不能直接替代运行内存。
- 部署方式标注“官方支持”或“本站已验证”，两者分别记录。
- 社区量化文件与官方原始权重分别注明来源。
- 简介与评价使用本站原创整理，保留引用链接；第三方内容的许可不随网站代码许可变化。
- 内容更新记录最后核实日期，历史评测保留其版本和日期，不包装成当前排名。

## 3. 页面与交互范围

| 页面 | 主要职责 |
| --- | --- |
| 首页 | 展示定位、搜索与用途入口、精选模型、近期更新 |
| 模型目录 | 搜索、用途、规模、许可和部署方式筛选，提供稳定的排序规则 |
| 模型详情 | 展示能力摘要、特点与限制、评测、运行条件、获取与部署 |
| 模型对比 | 最多 3 个同用途模型并排比较，明确不可比或缺失数据 |
| 部署指南 | 提供工具或任务通用步骤，链接至模型的具体差异 |
| 方法与贡献说明 | 说明收录规则、评测含义、来源、纠错与贡献方式 |

详情页阅读顺序：一句话介绍 → 场景与限制 → 能力证据 → 运行条件 → 获取与部署。

目录筛选条件可通过 URL 分享和恢复。对比使用稳定模型 ID，可通过链接分享；浏览器刷新和返回应保持合理状态。移动端筛选与对比必须具有完整入口。

## 4. 技术与发布架构

| 部分 | 首版选择 | 目的 |
| --- | --- | --- |
| 页面生成 | Astro 静态生成 | 构建时生成可索引页面，降低运行成本 |
| 局部交互 | React 按需加载 | 承担目录筛选、对比等交互 |
| 类型与内容校验 | TypeScript、Astro Content Collections | 在构建前后发现结构和关联错误 |
| 样式 | CSS 设计变量与组件样式 | 建立统一视觉规范，支持精细调整 |
| 动效 | CSS 优先，必要时使用 Motion | 处理状态反馈与复杂布局过渡 |
| 数据 | JSON + Markdown | 便于人工维护、审查、贡献和回滚 |
| 发布 | GitHub + Vercel | 使用预览部署审查，主分支更新后发布 |

维护流程：填写模板或导入 JSON → 校验 → 预览部署 → 检查内容与页面 → 合并发布。

首版搜索在客户端对精简索引执行，详情和长文不全部塞入搜索索引。只有实际数据规模或搜索质量证明有必要时，才引入专用搜索服务。

Vercel 只托管介绍、索引和轻量资源，模型权重与试玩链接指向相应官方平台。构建以仓库内已审查数据为输入，避免外部服务故障导致日常发布失败。

**前置条件：** 阶段一完成。

## 6. 实施与验收约定

- 每次修改先理解当前实现，优先复用已有组件和数据结构。
- 按相对独立的交付内容提交 Git，提交前执行与修改相关的检查。
- 使用项目自身配置的 Playwright 能力检查关键 Web 流程，不额外引入重复测试框架。
- 测试覆盖核心行为和真实边界，避免测试只复述实现。
- 测试结束后关闭本次启动的测试进程与浏览器页面。
- 功能更新同步维护 `docs` 中对应项目文档；存在源码后，按需建立和更新 Graphify，不进行语义提取。
- 每次中断或上下文恢复后，先检查 Git diff、任务状态和当前实现。
- 数据校验、构建通过、预览验证与正式上线分别记录，不以其中一项替代其他项。
- 本项目交付物为 Web 静态构建与部署，无需生成桌面 exe 或安装包。

## 7. 约束与后续决策

### 7.1 Vercel Hobby

Hobby 适用于个人非商业使用，仍有流量、请求、构建等额度。按 2026-10-01 查阅的官方说明，Fast Data Transfer 包含每月 100GB，CDN Requests 包含每月 100 万次；具体额度以发布时官方文档为准。

开源网站不自动等于符合 Hobby 条件。引入商业运营、广告或付费功能前，应复核套餐适用性。

Hobby Cron 最小执行间隔为每天一次，且不保证精确执行时间。后续采集优先独立运行于 GitHub Actions；GitHub 定时执行也可能延迟，公开仓库长期无活动时定时工作流可能被停用，因此保留手动触发与运行时间记录。

### 7.2 后续决策触发条件

| 情况 | 需要重新评估的选择 |
| --- | --- |
| 人工文件维护明显成为瓶颈 | 是否引入轻量 CMS 或在线管理 |
| 数据量或搜索质量超出客户端索引能力 | 是否引入专用搜索服务 |
| 确定需要账户或大量服务端功能 | 是否扩展服务端架构或采用其他框架 |
| 商业化或持续超出 Hobby 额度 | 部署套餐与成本预算 |
| 自动采集稳定且审核压力明显增长 | 是否有限开放低风险字段的自动更新 |

这些能力不提前建设；出现真实需求后明确范围、成本和验收条件，再调整方案。
